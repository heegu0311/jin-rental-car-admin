# 관리자 마이페이지 (2026-11-07)

## 동작

- 헤더의 고정 사용자 아이콘·관리자 문구를 로그인한 본인의 이메일 첫 글자(영문 대문자)와 표시 이름으로 변경했다. 아이콘은 모든 폭에서 보이며 이름은 모바일에서 숨긴다. 클릭/키보드 접근으로 `/mypage`에 진입한다.
- 대시보드 서버 레이아웃이 기존 `requireAdmin()` 결과에서 이메일·표시 이름·첫 글자만 클라이언트 셸에 전달한다. 추가 브라우저 프로필 쿼리나 관리자 목록 조회는 없다.
- 마이페이지는 프로필 설정과 계정 보안 패널을 재사용한다. 표시 이름만 수정하며 이메일은 읽기 전용이다. 이름은 줄바꿈/제어문자 없이 1~40자로 서버 검증해 `auth.updateUser({ data: { display_name } })`로 본인에게 저장한다. 저장 완료 후 레이아웃을 갱신해 헤더에도 반영한다.
- `display_name`이 없으면 기존 Google `full_name`/`name`, 없으면 이메일 아이디를 표시한다. 사용자 메타데이터는 표시용이며 권한 판정에는 쓰지 않는다.
- 비밀번호 변경 버튼은 이메일 계정에서 현재/새 비밀번호/확인 폼을 연다. 새 비밀번호는 기존과 같은 영문·숫자 포함 12~128자 규칙으로 서버 검증한다. `current_password`를 Auth 서버로 전달해 현재 비밀번호도 검증한다. 저장 함수는 서버 세션과 `profiles.role`을 다시 확인한다.
- 변경 성공 후 로그아웃하고 로그인 화면에 완료 안내를 표시한다. `unstable_rethrow`로 Next.js의 정상 리다이렉트를 실패 Sonner로 오인하지 않도록 처리한다. 로그아웃만 실패하면 변경 성공과 구분해 로그아웃 버튼을 제공한다. 현재 비밀번호를 잊은 경우 기존 찾기 화면으로 이동한다.
- Google 전용 계정은 현재 비밀번호가 없으므로 비밀번호 변경 버튼에서 이메일 재설정 흐름으로 안내한다. 실제 계정 설정/비밀번호 입력은 사용자가 직접 한다.
- `useSubmitLock`, 필드셋 비활성화, 폼 오류와 Sonner로 중복 제출과 실패 복구를 제공한다. 비밀번호나 이메일을 로그에 기록하지 않는다. 역할·공유 계약·의존성·잠금 파일·루트 layout·전역 CSS 변경 없음.

## 검증

- admin 테스트 42개, web 테스트 34개 통과. 양쪽 타입 검사·린트·프로덕션 빌드 통과. web의 첫 빌드는 Google Fonts 연결 제한으로 실패했으나 네트워크를 허용한 재실행은 통과했다.
- 새 순수 함수 테스트로 표시 이름 우선순위, 이메일 첫 글자, 이름 입력 제한을 확인했다. 비밀번호 서비스 테스트는 현재 비밀번호 전달, 잘못된 현재 비밀번호의 실패 처리와 로그아웃 차단을 확인한다.
- 별도 Next.js와 모킹한 Supabase HTTP 서버에서 로그인 → 헤더 프로필 클릭 → 마이페이지 → 이름 저장 → 헤더 반영을 실제 브라우저로 검증했다. 잘못된 비밀번호 확인과 현재 비밀번호의 오류/입력 보존, 정상 변경 → 로그아웃 → 로그인 완료 안내, 잘못된 실패 Sonner가 남지 않는 것도 확인했다. 테스트 계정과 비밀번호는 이 모킹 환경에서만 사용했다.
- 1440×900 및 390×900에서 가로 넘침 없음(문서 scrollWidth 1440 / 390). 모바일 메뉴 열기·닫기와 폼 라벨/필수 입력을 확인했다. 임시 스크린샷은 `/private/tmp/jin-account-check/mypage-{1440,390}.png`에 있다.
- 실제 운영 계정의 이름·비밀번호는 변경하지 않았다. Google 전용 계정의 실제 이메일 설정 흐름은 이 작업에서 재발송/브라우저 검증하지 않았다. 기존 이메일 재설정 기능을 사용한다.

## 적용 상태

admin main에 구현하고 로컬 커밋한다. web의 기존 작업은 보존하며 코드 push·사이트 배포는 수행하지 않는다. 마이페이지 자체의 새 DB 마이그레이션이나 환경변수는 없다. 같은 작업의 관리자 이메일 사전 검증용 마이그레이션은 별도 커밋과 [기록](admin-password-recovery.md)에서 관리한다.
